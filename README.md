# МЭКС analytics

Приложение на Streamlit для учёта протоколов конкурсов МЭКС (портал
электронных закупок `meks.zakup.sk.kz`): загрузка и разбор PDF-протоколов,
проверка/правка данных, хранение в PostgreSQL (Neon) — для дальнейшей
визуализации в Power BI. Дополнительно — полуавтоматический парсинг новых
конкурсов с портала и ИИ-прогноз баллов подрядчика по будущим конкурсам
(DeepSeek).

## Структура проекта

```
MEKS analytics/
├── app.py                              # точка входа, авторизация, главная страница
├── common.py                           # подключение к БД, логин, общий CSS/бренд
├── models.py                           # SQLAlchemy-модели (схема БД)
├── parser.py                           # разбор PDF-протоколов (pdfplumber)
├── crud.py                             # сохранение/чтение/журнал изменений
├── ui_components.py                    # общая форма редактирования тендера
├── scraper.py                          # парсинг портала meks.zakup.sk.kz (Playwright)
├── scraper_page.py                     # общий экран парсинга для обоих его разделов
├── ai_assistant.py                     # интеграция с DeepSeek + сборка отчёта в Word
├── requirements.txt
├── .env.example                        # шаблон настроек — скопировать в .env
├── .streamlit/config.toml              # тема, отключение телеметрии, toolbar
├── assets/logo.*                       # логотип BI Group (положить сюда вручную)
└── pages/
    ├── 1_📤_Загрузка_PDF.py             # загрузка и проверка PDF перед сохранением
    ├── 3_🔍_Просмотр_и_правка.py        # поиск и редактирование сохранённых тендеров
    ├── 4_📜_Журнал_изменений.py         # история изменений (кто/когда/что)
    ├── 5_🗺️_Региональность.py           # регион подрядчика/заказчика
    ├── 6_🌐_Парсинг_данных.py           # поиск и скачивание протоколов завершённых конкурсов
    ├── 7_🤖_ИИ_ассистент.py             # прогноз баллов подрядчика по будущему конкурсу
    └── 8_🚫_Парсинг_несостоявшихся.py   # то же, но по несостоявшимся конкурсам
```

Обе страницы парсинга — обёртки над одним экраном (`scraper_page.py`),
отличаются только статусом конкурса на портале: логика обхода, входа по ЭЦП
и скачивания у них общая, поэтому любое исправление действует сразу в обеих
и они не расходятся со временем.

(Нумерация страниц не сплошная — раздел «2, Ручной ввод» использовался на
раннем этапе и был убран за ненадобностью; переименовывать остальные не
стали, чтобы не плодить бессмысленный диф.)

## Запуск локально

1. Установите зависимости:
   ```
   pip install -r requirements.txt
   ```
   Для раздела «Парсинг данных» дополнительно нужен браузер Playwright
   (один раз):
   ```
   playwright install chromium
   ```

2. Скопируйте `.env.example` в `.env` и заполните:
   - `DATABASE_URL` — строка подключения к вашей базе в Neon
     (Neon Dashboard → Connection Details → используйте **Pooled
     connection**, она уже содержит `sslmode=require`)
   - `APP_USERNAME` / `APP_PASSWORD` — логин и пароль для входа в приложение
   - `AUTH_SECRET` — любая случайная строка (например,
     `python -c "import secrets; print(secrets.token_hex(32))"`); без неё
     после каждого перезапуска сервера все залогиненные пользователи
     будут разлогинены
   - `DEEPSEEK_API_KEY` — ключ API [DeepSeek](https://platform.deepseek.com),
     нужен только для раздела «ИИ-ассистент»; без него остальное
     приложение работает как обычно, а этот раздел покажет понятную
     ошибку вместо падения

3. (Необязательно) Положите файл логотипа в `assets/logo.png` (или `.svg`,
   `.jpg`) — он автоматически появится в боковой панели и на экране входа.
   Без файла вместо него показывается текстовая замена «BI GROUP».

4. Запустите:
   ```
   py -m streamlit run app.py
   ```

   Именно `py -m streamlit`, а не просто `streamlit`: на Windows команда
   `streamlit` часто не попадает в PATH, и запуск падает с «Термин
   "streamlit" не распознается…». Через `-m` модуль ищется тем же
   интерпретатором, которым ставились зависимости. На macOS/Linux
   аналогично работает `python3 -m streamlit run app.py`.

   При первом запуске процесса приложение само создаст все нужные таблицы
   в базе (`Base.metadata.create_all`, результат кешируется на время жизни
   процесса — см. «Производительность» ниже) — руками ничего создавать не
   нужно.

5. Откройте адрес, который выведет Streamlit (обычно `http://localhost:8501`),
   войдите под указанным логином/паролем.

## Разделы приложения

1. **Загрузка PDF** — загружаете файл, приложение разбирает его и
   показывает редактируемую форму со всеми найденными полями (заказчик,
   лоты, комиссия, заявки, критерии оценки). Ничего не попадает в базу,
   пока вы не нажмёте «Сохранить в базу» — можно поправить любое поле.
   Поддержаны два формата протокола, встречающиеся на портале («Протокол
   итогов конкурса» и «Протокол об итогах конкурса») — парсер сам
   определяет, какой из них перед ним. Если по названию конкурса или
   перечню закупаемых работ похоже, что это услуги технического надзора —
   показывается явное предупреждение, чтобы не сохранить их в базу
   по невнимательности.

   Протоколы **несостоявшихся** конкурсов загружаются здесь же и тем же
   порядком — по структуре они не отличаются от обычных. В таблице
   «Позиции закупки (лоты)» рядом с «Категорией работ» есть галочка «Не
   состоялся»: она **проставляется автоматически**, если в самом протоколе
   есть фраза «Признать закупку … несостоявшейся» (проверено на 296
   протоколах завершённых конкурсов — ложных срабатываний нет), и её можно
   снять или поставить вручную. Значение попадает в столбец `lots.is_failed`
   — по нему такие конкурсы фильтруются на дашборде.
2. **Просмотр и правка** — выбираете сохранённый тендер из списка, форма
   заполняется его текущими данными, правите и сохраняете — при этом
   старая версия записывается в журнал изменений. Здесь же — полное
   удаление тендера (с подтверждением по номеру конкурса).
3. **Региональность** — привязка региона Казахстана к подрядчикам и
   заказчикам: два связанных выпадающих списка (номер ↔ название региона),
   с возможностью добавить регион, которого ещё нет в списке. Регион
   заказчика хранится один раз в справочнике `customers`, а не отдельно на
   каждом его тендере — поэтому не нужно проставлять его заново для
   каждого нового конкурса того же заказчика.
4. **Парсинг данных** — полуавтоматический поиск новых завершённых
   конкурсов на портале и скачивание их протоколов итогов. Приложение
   само сравнивает список конкурсов на портале с тем, что уже есть в базе,
   и пропускает услуги технического надзора по названию конкурса. Часть
   таких конкурсов с нейтральным названием всё равно проскочит и
   скачается — вторая, более точная проверка (уже по перечню закупаемых
   работ из самого протокола) происходит на странице «Загрузка PDF» перед
   сохранением в базу, см. выше. Для скачивания портал требует входа по
   ЭЦП — открывается настоящее окно браузера, и входите в него вы сами;
   **приложение никогда не запрашивает и не видит пароль ЭЦП**. Файлы
   скачиваются в папку «Загрузки», в базу тендеров не попадают
   автоматически — их нужно отдельно загрузить через «Загрузка PDF» после
   проверки.

   **Только локально.** На облачном сервере раздел не работает и работать
   не может: для входа по ЭЦП нужно настоящее окно браузера на вашем
   компьютере. Приложение определяет запуск на сервере само (см.
   `scraper.is_headless_server`) и показывает там понятное сообщение
   вместо кнопки запуска — иначе прогон надолго вешал страницу и
   обрывался невнятной ошибкой связи.

   **Про скорость.** Портал кладёт в каждый элемент списка конкурсов весь
   документ объявления целиком: одна страница из 50 конкурсов весит ~42 МБ
   и приходит 17–32 секунды, а весь архив (~370 конкурсов) — это ~340 МБ.
   Поэтому обход идёт с ранней остановкой: свежие конкурсы лежат в начале
   списка, и как только подряд попадаются страницы, целиком состоящие из
   уже известных базе конкурсов, обход прекращается. При ежедневном
   запуске это 1–2 страницы вместо восьми. Галочка «Полный обход архива»
   отключает раннюю остановку — она нужна только при первом запуске на
   пустой базе или после долгого перерыва. Увеличивать размер страницы
   бесполезно: при `size=200` ответ (168+ МБ) уже не доходит вообще.
5. **Парсинг несостоявшихся** — то же самое, но по конкурсам со статусом
   «Конкурс не состоялся» (на портале их ~175 против ~370 завершённых).
   Устроено идентично: тот же обход с ранней остановкой, тот же фильтр
   технадзора по названию, тот же вход по ЭЦП и то же скачивание — на
   портале у несостоявшихся конкурсов лежит документ того же типа
   («Протокол итогов»), и сам протокол по структуре не отличается.
   У раздела своя история последней сессии (строки в `scrape_downloads`
   помечаются `scan_type`), так что два раздела не показывают друг другу
   чужие запуски. **Не запускайте оба парсинга одновременно** — портал
   считает лимит запросов по вам целиком, вдвоём они быстрее упрутся в
   HTTP 429.
6. **ИИ-ассистент** — прогноз баллов подрядчика по гипотетическому
   будущему конкурсу. Выбираете подрядчика, регион будущего конкурса и
   предполагаемую сумму — приложение собирает всю историю участия
   подрядчика (конкурсы, категории работ, суммы, число участников,
   результаты, баллы по каждому критерию) и список подрядчиков того же
   региона, отправляет всё это в DeepSeek и показывает прогноз баллов по
   критериям, итоговую оценку вероятности победы и рекомендации. Каждый
   сгенерированный отчёт сохраняется в истории (таблица `ai_reports`) и
   доступен для просмотра позже, а также скачивается как файл Word.
7. **Журнал изменений** — кто, когда, каким способом (загрузка PDF /
   ручная правка / назначение региона) и что именно изменил (было →
   стало).

## Важно про парсинг PDF

Парсер поддерживает оба шаблона протокола результатов конкурса,
встречающихся на портале, и на тестовых файлах распознаёт почти все поля
корректно (номер, даты, суммы, состав комиссии, статусы заявок,
победитель/второе место, все критерии оценки с баллами, включая случаи,
когда таблица отклонённых заявок или список лотов переносится на
несколько страниц PDF). Единственное слабое место — если название
конкурса в конкретном PDF переносится на несколько строк, из-за
особенностей генерации PDF на портале текст "Название конкурса" и "Адрес
заказчика" иногда извлекаются не в том порядке. Для этого и существует
экран проверки перед сохранением — поправить два текстовых поля вручную
занимает несколько секунд.

Обратите внимание: сам протокол не публикует фактическую предложенную
цену в тенге — только балл за критерий "Предложенная цена". Поле
"Цена, тенге" в заявках остаётся пустым, если не заполнить его вручную.

## Подключение Power BI

Power BI Desktop подключается к базе через встроенный коннектор
PostgreSQL (Npgsql) — тем же DATABASE_URL, что и приложение (host, база,
логин/пароль из строки подключения Neon). Если позже понадобится
публикация в Power BI Service с автообновлением — база в Neon уже
публично доступна по SSL, отдельный шлюз (gateway) не потребуется.

Схема нормализована специально под "звезду" в Power BI:
- `tenders` — измерение "Тендер" (ссылается на `customers` через `customer_id`)
- `customers` — измерение "Заказчик" (название + регион; один раз на
  заказчика, а не на каждый его тендер)
- `suppliers` — измерение "Поставщик" (включая регион)
- `bids` — факт "Заявка" (по одной строке на пару тендер-поставщик)
- `bid_criteria` — факт "Критерий оценки" (длинный формат: одна строка =
  один критерий одной заявки; новый критерий в новых протоколах не
  требует изменения схемы или модели в Power BI)
- `lots`, `commission_members` — вспомогательные таблицы. В `lots` есть
  признак `is_failed` — конкурс признан несостоявшимся; по нему такие
  конкурсы отделяются от обычных в отчётах. **Учтите:** после запуска
  раздела «Парсинг несостоявшихся» в базе окажутся и несостоявшиеся
  конкурсы, и существующие отчёты начнут считать их вместе с обычными,
  пока в них не добавлен фильтр по этому признаку.
- `audit_log`, `scrape_downloads`, `ai_reports` — служебные журналы
  (изменения через приложение, история парсинга, история ИИ-прогнозов) —
  для отчётности обычно не нужны, но доступны при необходимости

## Производительность

- `init_database()` (проверка/создание таблиц) кешируется через
  `st.cache_resource` и реально выполняется один раз за время жизни
  процесса, а не на каждый переход между разделами — без этого каждый
  клик по навигации означал лишний поход в Neon.
- На все внешние ключи в схеме есть индексы (см. `models.py`) — без них
  соединения (JOIN) при просмотре тендера или сборе истории подрядчика
  для ИИ-ассистента выполнялись бы полным сканированием таблиц.
- `DATABASE_URL` в `.env.example` указывает на **pooled**-эндпоинт Neon
  (домен с `-pooler.`) — это уже самый быстрый вариант подключения,
  отдельно настраивать пул на своей стороне не нужно.
- Загрузка тендера со всеми лотами/заявками/критериями идёт батч-запросами
  (`selectinload`) вместо запроса на каждую дочернюю запись отдельно.
- Шрифт Montserrat подключается через `<link rel="preconnect">` +
  `<link rel="stylesheet">`, а не через блокирующий CSS `@import`.

## Деплой на Render

**Вариант А — через Blueprint (рекомендуется):** в репозитории уже есть
`render.yaml` с корректными build/start-командами и регионом (`virginia` —
рядом с Neon, см. `DATABASE_URL`). В Render: **New → Blueprint**, укажите
этот репозиторий — Render сам создаст сервис по `render.yaml`. При первом
деплое он попросит ввести значения переменных окружения (`DATABASE_URL`,
`APP_USERNAME`, `APP_PASSWORD`, `AUTH_SECRET`, `DEEPSEEK_API_KEY`) — сами
значения в `render.yaml` не хранятся.

**Вариант Б — вручную:**
1. Запушьте этот репозиторий в свой GitHub.
2. В Render создайте **Web Service**, укажите репозиторий.
3. Environment: **Python 3**.
4. Build command: `pip install -r requirements.txt`
5. Start command: `python -m streamlit run app.py --server.port $PORT --server.address 0.0.0.0`
6. В Environment добавьте переменные `DATABASE_URL`, `APP_USERNAME`,
   `APP_PASSWORD`, `AUTH_SECRET`, `DEEPSEEK_API_KEY` — те же значения, что
   в вашем `.env`.

Если после деплоя в логах ошибка `streamlit: command not found`, при этом
в логах сборки видно, что streamlit успешно установился — значит дело не
в Build command, а в том, что Render заодно определил проект как Node.js
(из-за `package.json` встроенного Node-драйвера внутри пакета playwright)
и подмешал поверх Python своё Node-окружение, из-за чего PATH при запуске
ведёт не туда, куда pip ставил пакеты. Решение — start command именно
`python -m streamlit ...`, а не голое `streamlit ...` (см. `render.yaml`).
Если же в логах сборки установка streamlit вообще не запускалась — тогда
причина в другом: Build command не сохранился/не заполнен, поправьте в
Settings сервиса.

Раздел «Парсинг данных» на облачном сервере работать не будет и не должен
— ему нужен видимый браузер на компьютере пользователя для входа по ЭЦП
(headless-сервер для этого не подходит по замыслу, не только технически).
Используйте его локально, а остальные разделы — хоть локально, хоть после
деплоя.
